# Техническое задание (ТЗ)
## Универсальный AI-Gateway / GenAI-DLP — «Комплаенс-шлюз для безопасного использования LLM»

**Рабочее название:** *(placeholder)* LedgerShield / AI-Gate
**Версия ТЗ:** 0.1 (черновик для MVP)
**Статус:** проект
**Связь с предыдущими документами:** обобщение ТЗ «AI-gateway для 1С» (Доп-2) до продукта уровня всей организации; реализует рекомендацию из отчёта по рынку GenAI-DLP.

> **Правовая правка относительно ранних документов.** Закон РК об искусственном интеллекте — это **№ 230-VIII** (подписан 17.11.2025, действует с **18.01.2026**). Ранее в черновиках фигурировал «№ 256-VIII о регулировании ИИ» — это неточность: № 256-VIII — омнибус-закон к Цифровому кодексу (№ 255-VIII), вступающему в силу **11.07.2026**. В этом ТЗ используются уточнённые ссылки: **ст. 12** (локализация хранения) и **ст. 16** (трансграничная передача) Закона № 94-V, **ст. 79 КоАП** (максимум **2000 МРП**).

## 1. Назначение и цели

### 1.1. Проблема
Сотрудники массово отправляют конфиденциальные данные во внешние LLM (ChatGPT, Claude, Gemini) через множество каналов: браузер (копипаст договоров, клиентских баз), IDE (исходный код, секреты), внутренние RAG-ассистенты, ERP/CRM, пайплайны автоматизации. По отраслевым данным, около 40% взаимодействий с ИИ-инструментами содержат чувствительные данные. Для организации в РК это одновременно:
- утечка коммерческой тайны и секретов (API-ключи, `.env`, исходники);
- нарушение Закона РК № 94-V: отправка ПДн граждан РК во внешнюю LLM = **трансграничная передача** (ст. 16) поверх обязанности хранить первичную базу ПДн в РК (ст. 12); штраф по ст. 79 КоАП — до **2000 МРП** (≈8,65 млн тг в 2026 г.), плюс риск блокировки ресурса.

Существующие глобальные продукты (Nightfall, Harmonic, Microsoft Purview, Zscaler) закрывают часть каналов, но **не дают data residency в РК, русскоязычных политик и on-prem под Закон № 94-V**, а классические DLP-вендоры СНГ пока не имеют нативной обратимой маскировки промптов к LLM.

### 1.2. Цель продукта
Единый шлюз, который перехватывает обращения к LLM по **всем ключевым каналам**, детектирует чувствительные данные, обратимо маскирует их (или блокирует по политике) перед отправкой и восстанавливает в ответе, с полным аудитом для комплаенса. Продаётся не «маскирование», а **право легально и безопасно пользоваться LLM всей организацией** + on-prem + локальная поддержка.

### 1.3. Ров (что защищаем от глобальных игроков)
Не «лучше детект, чем у Nightfall», а: **on-prem + data residency в РК + готовые политики под Закон № 94-V и Закон об ИИ № 230-VIII + русскоязычная поддержка + распознавание БИН/ИИН/казахской специфики**. Ров регуляторный и локализационный, не алгоритмический.

## 2. Термины и сокращения

| Термин | Значение |
|---|---|
| **Gateway** | Прослойка, встающая между источником запроса и LLM |
| **Канал** | Источник обращения к LLM: браузер, IDE, RAG/приложение, ERP, API/пайплайн |
| **PII / ПДн** | Персональные данные |
| **БИН / ИИН** | Бизнес- / индивидуальный идентификационный номер РК (12 цифр) |
| **Секрет** | API-ключ, токен, пароль, содержимое `.env`, приватный ключ |
| **Токенизация** | Обратимая замена чувствительного значения на плейсхолдер |
| **Mapping Store** | Локальная эфемерная таблица «токен ↔ значение» |
| **Провайдер** | LLM (внешний: OpenAI/Anthropic/Gemini; или локальный) |
| **Политика** | Правила: что маскировать / блокировать / пропускать, по каналу/группе/провайдеру |
| **Control Plane** | Управляющий контур: политики, RBAC, дашборды, отчёты |

## 3. Область применения и ограничения

### 3.1. В охвате MVP (по рекомендации отчёта)
- **Канал «Браузер»**: перехват отправки данных в веб-интерфейсы ChatGPT/Claude/Gemini.
- **Канал «Egress / внутренние системы»**: reverse-proxy / API-middleware для внутренних RAG-ассистентов, корпоративных приложений и пайплайнов (n8n/Make/прямые API-вызовы), ходящих во внешние LLM.
- Ядро: детект + обратимая токенизация (ИИН/БИН/ФИО/счета/секреты) + политика + форвард к **одному** провайдеру + обратная подстановка + tamper-evident аудит.
- Развёртывание **on-prem**.

### 3.2. Вне охвата MVP (закладывается архитектурно)
- IDE-канал (Copilot/Cursor через hooks), endpoint-агент для clipboard/локальных приложений (Claude Desktop).
- Коннекторы ERP/CRM (1С, Bitrix24) — этап 2.
- Мультипровайдерность, локальная LLM «из коробки», MCP/агентный слой — этап 3.
- ИИ-детект контекстных (не шаблонных) утечек по смыслу.

### 3.3. Правовые ограничения (обязательны)
- **Локализация (ст. 12):** Mapping Store, аудит и все ПДн — только внутри периметра/страны клиента; on-prem обязателен для РК.
- **Трансграничная передача (ст. 16):** по умолчанию наружу уходит только обезличенный текст; пропуск неочищенных ПДн — только при явном разрешении, с фиксацией основания и предупреждением.
- **Закон об ИИ № 230-VIII (с 18.01.2026)** и сопутствующий № 232-VIII (ст. 641-1 КоАП) — проверить требования к ИИ-компонентам продукта (юрист).

### 4.2. Ключевые решения (и почему)

- **Мультиканальные адаптеры + единое ядро.** Каналы отличаются только способом перехвата; детект/токенизация/политика/аудит — общие. Почему: не переписывать логику под каждый канал; новый канал = новый адаптер, а не новый продукт. Это тот же платформенный принцип, что и в ТЗ Доп-3.
- **Обратимая токенизация, а не затирание.** Значения → плейсхолдеры, локальный маппинг, восстановление в ответе. Почему: пользователю нужен осмысленный ответ, а не текст с `[REDACTED]`.
- **Fail-closed по умолчанию.** Ошибка детекции/парсинга → блок, а не «пропустить как есть». Почему: цена ложного пропуска (утечка ПДн + штраф) выше цены ложной блокировки. Это отличает комплаенс-продукт от «удобной обёртки».
- **Всё чувствительное — локально.** Mapping Store и аудит внутри периметра. Почему: ст. 12; вынос маппинга наружу сам был бы нарушением.
- **Egress-контроль как «страховочная сетка».** Даже если браузерный адаптер обошли (personal-девайс), reverse-proxy на периметре ловит обращения приложений/пайплайнов. Почему: ни один одиночный канал не даёт полного покрытия — нужна комбинация.

### 4.3. Сравнение способов перехвата (какой канал что покрывает)

| Способ | Что видит | Плюсы | Минусы | В MVP |
|---|---|---|---|---|
| **Browser extension** | Ввод/вставку в веб-LLM | Массовый канал; лёгкий деплой через GPO/MDM | Обходится на personal-девайсах; только браузер | **Да** |
| **Reverse-proxy / API middleware** | Обращения приложений/RAG/пайплайнов/API к LLM | Полный egress-контроль внутренних систем; per-decision аудит | Не видит E2E-трафик personal-девайсов | **Да** |
| **Endpoint-агент** | Clipboard, локальные приложения (Cursor, Claude Desktop) | Ловит то, что не видит сеть и браузер | Тяжелее деплой; права на машине | Этап 1.5 |
| **Forward proxy / SASE** | Сетевой трафик к AI-доменам | Без агента на каждой машине | Не видит E2E и локальные приложения | Опц. |
| **IDE hooks** | Промпты/действия из Copilot/Cursor | Точечно по разработке | Узкий канал | Этап 2 |
| **ERP/CRM connector** | Запросы из 1С/Bitrix24 | Вертикальный ров | Завязка на версии ERP | Этап 2 |

> Типичная ошибка: полагаться только на сетевой (SASE) перехват. Он не видит E2E-трафик и локальные приложения (Claude Desktop, Cursor, локальные MCP-серверы). Поэтому MVP = browser (массовый канал) + reverse-proxy (внутренние системы), а не «один сетевой прокси на всё».

## 5. Функциональные требования

### 5.1. F1. Мультиканальный приём (ingestion)
- **Браузер:** расширение для Chrome/Edge/Firefox, перехватывающее отправку текста в целевые веб-LLM (ChatGPT/Claude/Gemini): при вводе/вставке/сабмите текст проходит через ядро до фактической отправки.
- **Egress:** reverse-proxy / API-endpoint, на который перенаправляются обращения внутренних приложений, RAG-ассистентов и пайплайнов (n8n/Make/прямые API-вызовы) к LLM.
- Единый внутренний формат «запрос на проверку» независимо от канала.

### 5.2. F2. Детект и классификация чувствительных данных
Минимальный набор MVP:
- **ИИН** (12 цифр; первые 6 — дата рождения YYMMDD, 7-я — век/пол; контрольная сумма по взвешенному алгоритму) — валидировать по формату **и** контрольной сумме.
- **БИН** (12 цифр; своя структура и контрольная сумма) — отличать от ИИН по управляющим разрядам.
- **ФИО** (включая казахские форматы `-улы/-кызы/-тегі`).
- **Счета/карты** (IBAN KZ, PAN).
- **Секреты**: API-ключи, токены, пароли, содержимое `.env`, приватные ключи (по паттернам + энтропии строк).
- **Суммы/балансы** (по контексту, настраивается).
- **Исходный код** и маркеры коммерческой тайны — по настраиваемым словарям/правилам (расширяется на этапе 2).

> Требование точности: детект ИИН/БИН обязан использовать контрольную сумму, иначе либо ловит любые 12-значные числа (ломает смысл), либо пропускает валидные (утечка). Точную схему контрольной суммы реализовать по официальной спецификации РК. Детект секретов — комбинация регэкспов известных форматов и оценки энтропии.

### 5.3. F3. Обратимая токенизация
- Замена сущностей на типизированные плейсхолдеры (`[IIN_1]`, `[BIN_1]`, `[PERSON_1]`, `[SECRET_1]`, `[ACCOUNT_1]`).
- Локальный Mapping Store с TTL; консистентность в пределах запроса (одно значение → один токен); гарантированное уничтожение маппинга после ответа.

### 5.4. F4. Политики (Policy Engine)
- Режимы на сущность: `mask` / `block` / `allow` (последний — только с явного разрешения + логирование как трансграничная передача).
- Правила по каналу, группе пользователей (RBAC), провайдеру.
- Глобальный **fail-closed** при ошибке.

### 5.5. F5. Форвард к LLM
- Отправка **обезличенного** текста выбранному провайдеру (MVP — один).
- Ключи провайдера — в защищённом хранилище на стороне gateway (не в браузере, не в приложениях).
- Задел под мультипровайдер и локальную LLM.

### 5.6. F6. Обратная подстановка
- Замена плейсхолдеров обратно на значения из Mapping Store в ответе LLM; возврат в исходный канал; уничтожение маппинга.

### 5.7. F7. Аудит и отчётность (tamper-evident)
- Лог: пользователь, канал, время, **типы и количества** замаскированных сущностей (без значений), провайдер, вердикт политики.
- Неизменяемый (append-only) локальный лог для проверок регулятора.
- Комплаенс-отчёт: «за период N запросов, замаскировано M ПДн, K блокировок, 0 утечек в открытом виде».

### 5.8. F8. Control Plane
- Admin console: политики, RBAC, дашборды, отчёты, конфигурация провайдеров.
- Локальное развёртывание всего управляющего контура.

## 6. Модель данных

- **Policy**, **MappingEntry** (`token↔value`, session_id, TTL — эфемерно, локально), **AuditRecord** (без значений — только типы/счётчики), **Provider** (endpoint + ключ в secret storage), **DetectorRule**, **User/Group/Role** (RBAC), **Channel**.
> Privacy by design: значения ПДн живут только в эфемерном MappingEntry с TTL; в аудите значений нет.

---

## 7. Нефункциональные требования

### 7.1. Латентность (gateway в разрыве запроса)
- Накладные расходы (детект + токенизация + detokenize) — цель **< ~200 мс** на типовой запрос (без времени LLM); таймауты и корректная деградация при недоступности провайдера.

### 7.2. Точность (метрика ценности)
- ИИН/БИН/секреты: **recall близкий к 100%** (пропуск недопустим) при приемлемом precision; на неоднозначных данных — склоняться к маскированию (fail-safe).

### 7.3. Масштаб и совместимость
- Браузеры: Chromium-семейство + Firefox. Провайдер: один на MVP. On-prem-инсталляция контейнеризирована (Docker/Compose; Kubernetes позже).

### 7.4. Локализация
- On-prem обязателен для РК; весь чувствительный контур внутри страны; исходящие соединения — только сам вызов LLM.

## 8. Требования безопасности самого gateway (повышенный приоритет)

Gateway видит данные в открытом виде **до** маскирования — его компрометация = утечка всего. Поэтому:
- Шифрование Mapping Store и секретов провайдеров; эфемерность маппинга (TTL + гарантированное уничтожение).
- RBAC и аутентификация доступа к gateway и консоли; mTLS во внутреннем контуре.
- Аудит доступа к самому gateway (кто менял политики, кто смотрел логи).
- **Логи не содержат исходных ПДн/секретов** (частая ошибка — залогировать полный запрос «для отладки»).
- Подпись расширения/агента; защита каналов доставки обновлений.

---

## 9. Требования к развёртыванию

- **On-prem / внутристрановой** — обязательный режим для РК.
- **SaaS** — только для сценариев без ПДн РК; по умолчанию продвигать on-prem.
- Поставка: контейнеры ядра + Control Plane; браузерное расширение через корпоративный деплой (GPO/MDM); инструкции подключения egress-канала.

## 10. Этапы разработки (совпадают с рекомендацией отчёта)

| Этап | Содержание | Результат |
|---|---|---|
| **Э0. Каркас** | Ядро (Ingress→Detector→Tokenizer→Policy→Forwarder→Detokenizer→Audit) + Control Plane + один провайдер | Проксирующее ядро без каналов |
| **Э1. MVP (0–6 мес.)** | Канал «Браузер» + канал «Egress/reverse-proxy»; детект ИИН/БИН/ФИО/счета/секреты; обратимая токенизация; fail-closed; аудит; on-prem | **Продукт под пилот в BFSI/госсекторе РК** |

## 11. Критерии приёмки MVP (Э1)

MVP принят, если на тестовом стенде:
1. При отправке в веб-ChatGPT/Claude/Gemini текста с ИИН/БИН/ФИО/секретом наружу уходит текст **без единого** из этих значений в открытом виде (проверяется перехватом исходящего трафика).
2. Ответ LLM возвращается в канал с **корректно восстановленными** значениями.
3. Внутренний RAG/приложение, направленное на egress-proxy, так же маскируется и восстанавливается.
4. Детект ИИН/БИН работает по контрольной сумме (не маскирует произвольные 12-значные числа и не пропускает валидные); детект секретов ловит типовые API-ключи/`.env`.
5. При сбое детекции/парсинга срабатывает **fail-closed**.
6. Весь чувствительный контур (Mapping Store, аудит, консоль) работает **on-prem без исходящих соединений**, кроме самого вызова LLM.
7. Формируется tamper-evident комплаенс-отчёт без раскрытия значений в логах.

## 12. Риски и открытые вопросы

- **Enterprise-режимы LLM (no-training, ZDR) снижают аргумент «утечка в обучение».** Митигация: главный аргумент в РК — не обучение, а **локализация и трансграничная передача** (данные физически покидают РК независимо от режима); плюс контроль секретов/кода, который enterprise-режим не решает.
- **Крупные платформы (Microsoft Purview, Zscaler, Palo Alto, SentinelOne) покрывают AI-DLP как фичу.** Митигация: не конкурировать «в лоб» глобально; защищать локальный/регуляторный ров (on-prem РК, русские политики, БИН/ИИН, ERP/1С).
- **Обход браузерного канала на personal-девайсах.** Митигация: комбинировать с egress-контролем и endpoint-агентом; политики на корпоративных устройствах через MDM.
- **Неполный детект = утечка = штраф у клиента.** Митигация: fail-closed, приоритет recall, честное позиционирование «инструмент снижения риска», корректные формулировки ответственности в договоре (юрист).
- **Латентность** ухудшит UX. Митигация: лёгкий детект, кэш, асинхронность.
- **Локальные DLP-вендоры СНГ (InfoWatch/Solar/SearchInform)** могут добавить LLM-DLP. Митигация: скорость выхода + ERP/1С-вертикаль + on-prem-ниша.
- **Правоприменительная практика по «трансграничной передаче в LLM» в РК не устоялась** — позиционирование строить на тексте ст. 12/16, но без обещаний «100% соответствия»; следить за разъяснениями регулятора и Законом № 230-VIII.

## 13. Что решить до старта

1. Порядок каналов MVP подтверждён: браузер + egress (reverse-proxy). Endpoint-агент — сразу после.
2. Ядро детекта: Presidio + собственные recognizer'ы под БИН/ИИН/казахские имена/секреты, или полностью своё. Presidio ускоряет MVP — проверить лицензию и качество на казахской специфике.
3. Первый провайдер LLM для форварда.
4. Пилотные клиенты: 3–5 из банков/госсектора РК, где сотрудники уже (неофициально) используют веб-LLM.
5. Юридическое сопровождение: формулировки ответственности, соответствие ст. 12/16 Закона № 94-V и Закону об ИИ № 230-VIII — до первых продаж.
6. Модель монетизации: per-seat (браузер) + enterprise on-prem лицензия (egress/ERP); ориентир для РК — с поправкой на локальную платёжеспособность.
